# Design decisions

One row per decision that creates a rule. A decision that is a picture belongs on a
canvas and then in a project's own documentation; this file is for the rules.

Newest last. Never rewrite a row: supersede it with a new one that says so.

| Date | Question | Answer | Rule it creates |
|---|---|---|---|
| 2026-09-08 | One repository per Orbiters project, or one for all of them? | One monorepo, with a directory per project under `projects/`. | A project owns everything under `projects/<name>/`, including its own docs, Dockerfiles and deploy scripts. |
| 2026-09-08 | Per-project lockfiles, or one per language for the whole repository? | One `uv.lock` and one `pnpm-lock.yaml`, both at the root. | Two projects can never resolve the same library at two versions. A project needing an incompatible pin leaves the workspace, with the reason written down. |
| 2026-09-08 | Where do build-and-test dependency versions live? | In `pnpm-workspace.yaml`'s `catalog:`. | A package writes `"typescript": "catalog:"`. What a project *ships* stays in its own `package.json`; what it needs in order to be built, linted and tested is monorepo policy. |
| 2026-09-08 | Do a project's design documents move to a shared `docs/` at the root? | No. They stay inside the project. | `docs/` at the root is about the monorepo only. A test that reads a note as a contract keeps working, and a project stays extractable. |
| 2026-09-08 | Per-project `pyproject.toml` for pytest and mypy configuration? | No. Both stay at the root and name each project's paths in full. | Everything runs from the repository root; CI narrows to one project by passing its paths. A config that only resolves when you have `cd`'d into a directory silently checks nothing when you have not. |
| 2026-09-08 | One CI workflow per project, or one workflow calling shared gates? | One `ci.yml`, calling `_python-gate.yml` and `_node-gate.yml` through `workflow_call`. | Adding a project costs a filter and a job, never another CI workflow. Deploy is the exception and is always per project. |
| 2026-09-08 | Which status check does the trunk require? | `ci`, the aggregate job, and only it. | Job names below `ci` can change forever without a ruleset edit. (Not yet enforceable: the org is on the Free plan and the repository is private, so rulesets are unavailable.) |
| 2026-09-08 | Rename the `PIGROCRM_*` namespace now that the repository is not just PigroCRM? | No. | Environment variables, distribution names, the CLI and the databases stay project-scoped. The project is still called PigroCRM. |
| 2026-09-08 | Which language does repository-facing text use? | English, everywhere: docs, README, AGENTS.md, issues, PR and commit messages, code comments. | A product's user-facing strings stay in the language its users read, which for PigroCRM is Italian. Existing Italian specs under `projects/pigrocrm/docs/superpowers/` are not retranslated; anything written from now on is English. |
| 2026-09-08 | One Linear project for the monorepo, or one per project? | One per project, in the `Orbiters` team. | A new project opens its own Linear project (`docs/adding-a-project.md` §9). `Area` labels are shared across projects; priority is Linear's native field, not a label. |
| 2026-09-09 | When does a project deploy? | Preview on every push to `main` that touched it; production only on a project-scoped version tag `<project>-v<semver>`. | A push to main means the trunk moved, which is worth seeing on a real server and is not worth putting in front of the person who uses the product every day. A bare `v1.2.0` in a monorepo does not say which project it releases. |
| 2026-09-09 | Where does per-environment deploy configuration live? | In GitHub Environments (`<project>-preview`, `<project>-production`), each holding the same four secrets: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_SSH_KEY`. | Prefixed repository secrets would grow one name per project per environment. Four names that never change scale; forty names do not. Environments also carry deployment history and are where a production reviewer goes once the plan allows it. Callers must pass `secrets: inherit` or a reusable workflow reads them as empty strings. |
| 2026-09-09 | One deploy workflow, or one per project? | One shared mechanism (`_deploy-compose.yml`) plus a short caller per project. Deploy is still never triggered across projects. | The earlier rule said the whole workflow is per project, which duplicated ssh, rsync, the CI gate and the health check on every new project. The trigger stays per project, which is the part that must never be shared; the steps do not. |
| 2026-09-09 | The public pages lived inside the CRM's web app. Where do they belong? | Their own project, `projects/website`: it is joinorbiters.com, a site of its own that will grow past a landing page, not a corner of the CRM. | It builds in 300ms with no framework, and it was being carried by an application build that takes twenty times that. Extracting it also removed 394 bytes of dead CSS from the application, generated by Tailwind scanning the website's own JavaScript (`addEventListener('resize')` produced a `.resize` utility nothing rendered). One deployable still serves both today: ORB-12 carries splitting the serving, which moves two live domains. |
| 2026-09-09 | Two surfaces, one brand: where do the palette and the typeface live? | `shared/brand`, a workspace package both projects depend on. The application reads it as part of its Tailwind theme; the website extracts it at build time, having no Tailwind at all. | There must be one source of colour and no copy. `--radius` deliberately stayed with the application: the website's system is square by design. Verified by diffing the emitted CSS before and after the move: byte-identical, same font asset hash. |
| 2026-09-09 | What language is this repository written in? | English, everywhere: docs, code, comments, commit messages, Linear. The only exception is what the product says to its users, which stays in the user's language (Italian for PigroCRM). | Supersedes the 2026-09-08 row, which only covered documentation. A repository half in one language cannot be handed to a contributor, and this one is meant to be open-sourceable. The dated records under `docs/superpowers/` are grandfathered: rewriting a record is how it stops being a record. |
| 2026-09-09 | May a project be a single package at its own root, instead of `apps/*` plus `packages/*`? | Yes, when it is one artifact. `projects/website` is four HTML pages and three scripts. | An `apps/` directory with exactly one entry in it is ceremony. The pnpm workspace matches `projects/*` as well, and a directory without a package.json is simply not a package. |
| 2026-09-09 | Where does the ChatGPT Ads pixel go, and who holds its key? | The pixel initialises on the two pages an ad can land on (`index.html`, `orbiters.html`) and on neither legal page; the conversion is measured twice -- in the browser and from the API -- sharing one event id; the Conversions API key lives only in the server's `.env`, and `pigrocrm conversions-check` is how it is verified. | A tracker on a privacy policy cannot be defended, and the browser event is the one that gets blocked, so the server half is what makes the numbers real. One shared id is what keeps the pair from counting as two. The key has full read and write access to the conversion source and cannot be scoped, so nothing that is served to a browser or committed may contain it. |
| 2026-09-09 | Does the measurement pixel wait for consent? | Yes, and it is not loaded at all until somebody says yes: `consent.js` shows a small notice and injects the SDK only on acceptance, so before a decision the browser makes no request to OpenAI. A refusal is remembered and not asked again. | A tracker that fetches its own script before the answer has already handed a third party the visitor's IP and user agent, which is the thing consent exists to decide -- so `oaiq('consent', false)` after the snippet would have been a notice about something that already happened. Refusing has to cost the same one click as accepting, or it is not consent. |
| 2026-09-09 | Where does the root installation log in, and where do its cookies live? | At the bare `/app/login` (and `/app/registrati`), which nginx never redirects under the root's name; the root's session cookies are `Path=/` even when the request wore `/<root_slug>/`. | After a logout nobody is in a space, so the address must not name one. One jar at `/` is the only thing the bare login and the aliased app can both read; a space keeps `/<slug>/`, and the API reads the most specific cookie first so a root cookie never shadows a space's own. |
| 2026-09-09 | Does PigroCRM have a running timer, after slice 4 §13 argued against one? | Yes, one per user, as a server row (`time_timers`) that becomes an ordinary time entry when stopped; the weekly grid stays as the second view of `/app/ore`. | Ivan asked for the Toggl/Clockify shape. A row on the server is one mechanism, not three: the closed browser and the second device both just read it back, and `stop` goes through `TimeEntryService.create`, so nothing about how an hour is valued changed. Spec: `projects/pigrocrm/docs/superpowers/specs/2026-09-09-time-tracking-timer-and-register-design.md`. |
| 2026-09-09 | The website was built into the CRM's image and served at its document root. Split the serving too? | Yes: its own image, its own compose stack on 127.0.0.1:8082, its own vhost and its own `website-v<semver>` tag. | A copy change was waiting for a CRM release, and a CRM rollback took the public site with it. The two have different release rhythms and nothing in common but a brand. `_deploy-compose.yml` already took a project and an environment, so this cost a caller and two GitHub environments, not new machinery. |
| 2026-09-09 | After the split, `pigro.joinorbiters.com/pigrocrm`, `/privacy`, `/termini` and `/orbiters` still answered from the CRM's image. Keep a second copy? | No: 301 to joinorbiters.com, and the CRM's image stops building the site. | A policy page with two live copies is a policy page that gets edited in one of them. The redirect keeps every old link alive at the cost of one hop. |
| 2026-09-09 | One deployable starts serving what another served. Which lands first? | The new one goes up and takes the name first; the old one stops building it afterwards, in a later commit. | Production here is deployed from `main` by hand, so a merge is a release. Doing it in the other order took joinorbiters.com down to redirects for twenty minutes (ORB-16). The safe direction costs nothing: an unpointed container can run for days. |
| 2026-09-09 | Where does Orbiters live in the monorepo? | In `projects/hub`, as a product of its own: its own Postgres, its own API (`orbiters_api`), its own MCP server (`orbiters_mcp`), its own Alembic history. Nothing of it stays in `pigrocrm-*`, and neither product imports the other (`projects/hub/ruff.toml` bans the `pigrocrm*` roots). | Ivan asked for the split on 2026-09-09: the community and the CRM are two products with two audiences, and a change to one must never be a deploy of the other. The signup table is adopted where it stands (migration 0001 is all `IF NOT EXISTS`); `pigrocrm conversions-check` is now `orbiters conversions-check`. Spec: `projects/hub/docs/superpowers/specs/2026-09-09-orbiters-hub-design.md`. |
| 2026-09-09 | What is a «logged work day», and what is a «deadline»? | A day is hours on a deal -- an ordinary `time_entries` row, with «giornata» as an eight-hour preset -- and a deadline is an `attivita` (slice 7's table, built now) with a nullable `scadenza`. The calendar also *shows* invoice due dates and cannot change them. | The hours model requires a deal because the P&L and the invoicing do (slice 4), and a second «day» concept outside it would be a diary that no report can read. A due date on an invoice is a property of the document, decided at issue: editable from a view showing neither number nor amount, it would be a fiscal document changed from the wrong place. |
| 2026-09-09 | Does the trunk tier run everything on every commit, or is it path-scoped like the PR tier? | Path-scoped, by the same filters, with `all=true` when the push has no reachable base commit. | This repository is private, so every Actions minute is billed, and it burned 1,564 of a 2,000/month allowance in eight days. Running the CRM's twelve-minute suite on a push that only touched the website bought nothing. The property given up is "the trunk proves the whole tree on every commit"; what keeps it honest is that a change to a shared root file (`uv.lock`, `pnpm-lock.yaml`, `pyproject.toml`, `shared/brand/`) selects everything. |
| 2026-09-09 | A deploy refuses a commit CI has not passed. Does it wait for CI, or is it triggered by it? | Triggered by it: the preview runs on `workflow_run` when CI concludes green on `main`, reads what changed from the artifact `changes` published, and deploys `github.event.workflow_run.head_sha`. Production stays on the tag push. | Waiting was a `sleep 30` loop on a metered runner: measured on one preview, 458 of 514 billed seconds were the wait and 51 were the deploy. The guarantee is unchanged, since `_deploy-compose.yml` still asks the API which run covers that commit. Two consequences are load-bearing: `github.sha` on a `workflow_run` event is the branch tip at event time, so the verified sha has to be passed explicitly, and such a workflow only ever runs in its default-branch version, so these files cannot be tested from a branch. |
| 2026-09-09 | May a release ever be done by hand on the server? | No. Every stack, preview or production, is released only by its deploy workflow: preview on a green trunk run, production on a `<project>-v<semver>` tag. A deploy that is not armed gets armed (environment, the four secrets, the variable); nothing ships by hand in the meantime. Since 2026-09-09 all three stacks (`pigrocrm`, `website`, `hub`) are armed and have released this way. | Ivan, 2026-09-09, twice: «rilasciare fatto tramite CI sempre», then «va rilasciato tutto, no deploy manuali». `docker compose up`, `rsync` or `git pull` on the server are not a release; ssh is for reading state and for operations that are not a release (cron, `.env`, `createadmin`, the vhost). The deploy refuses a commit whose CI is not green, and that guarantee only exists while the deploy is the one path. |
| 2026-09-09 | May the cookie notice cover the page while it waits for an answer? | No. On a phone the whole community page fits one screen, so what the fixed notice covers stays covered. While it is up, consent.js measures it and writes `--consent-room` on the root; system.css spends it as a spacer at the end of the body, not as body padding, so neither page's own padding arithmetic has to know about it. Both go away with the notice. | The notice never covers content, on any page that carries it. `body::after` in system.css is the one place the room is spent, and no other rule owns that pseudo-element. |
| 2026-09-09 | Who is Orbiters for, and where is that written down? | `docs/design/positioning.md`: software developers, AI engineers, CTOs and fractional tech roles working on their own account, at a seniority where a company can hand them a project. «Freelance» stays the legal and fiscal category and stops being the headline. | Every public surface follows the statement: titles, meta and Open Graph, the two `h1`s, the calls to action, the hub's public pages, MCP descriptions. A copy change that departs from it changes the statement first. Routes, API and database vocabulary keep `freelance` as the category name (ORB-24 point 4); `shared/brand` is unchanged by this decision, and the identity verdict in the same file is an argument, not a change. |
| 2026-09-09 | Under the forfettario, does every line carry `N2.2`, or does the customer's country decide? | The country decides: `N2.2` with the profile's L. 190/2014 declaration for an Italian customer (an empty country is Italy, the column's default); `N2.1` for a customer established abroad, with the annotation art. 21 c. 6-bis DPR 633/1972 prescribes: "inversione contabile" for a customer in another EU member state, "operazione non soggetta" outside the EU. `issue` asks the regime again for every stored line and refuses, before the number is consumed, when a line disagrees; `replace_lines` is the remedy. The PDF footer prints the declaration the lines carry, not the profile's text. | A service to a business outside Italy is outside the territorial scope of Italian VAT (art. 7-ter), and the accountant's register already says N2.1 for those invoices (ORB-32). The regime strategy takes the customer's `nazione`, keyword-only and without a default, so nothing can get the domestic answer by omission; `InvoiceLineIn` still refuses a caller-supplied `natura`. The texts and the EU set are constants, not profile columns, because the profile describes the issuer and this depends on the customer. Spec 7.2 of slice 3 recorded the old rule and is not rewritten. |
| 2026-09-09 | For a customer outside Italy, who applies the SdI's `00000` convention for `CAP`: the person entering the record, or the exporter? | The exporter. `_sede` writes `CAP` as `00000` and omits `Provincia` whenever `Nazione` is not `IT`, whatever the customer row holds, and appends the real postcode to `Indirizzo` (`"1 Old Street, EC1V 9HL"`) so the document keeps it; a record that already holds `00000` gets the address alone. `check_party_exportable` measures the same composite against the 60-character bound and requires `comune` of every party, so a foreign address it accepts is one `export_xml` can serialise. An Italian CAP that is not five digits stays refused before the number is consumed. | The customer record holds the address as it is, the PDF prints it, and the file says what the technical specifications for FatturaPA 1.2.x prescribe for a foreign address (`CAP` `00000`, no `Provincia`, `IdPaese` the customer's country). Asking a London company to type `00000` as its postcode was a lie in the record (ORB-38); refusing a real postcode after `issue` had spent the number left annulment as the only remedy. Rule: what the pre-check accepts, the writer serialises, and the one place the two texts differ (`Indirizzo` with the postcode) is a single shared function. |
| 2026-09-09 | Two of us run agents against one board, and each took cards the other had filed for himself (ORB-25, and the same in the other direction). What decides who may work an issue? | The `assignee` field, as a claim: an agent works a card assigned to the account its session writes as, or one with no assignee that it filed itself, or one labelled `parallel` that nobody has claimed. Every issue is filed with an assignee, and the first read of a session establishes which account that is (`get_user` with `"me"`, keeping the id). | A card assigned to somebody else is untouched: no assignee change, no status change, no branch, no PR, nothing re-parented under it, a comment at most, and being asked for it by name does not make it yours. The project lead does not own the project's issues; the lead decides, the assignee works. `parallel` opens an unclaimed card to whoever is free, whoever filed it, and never reopens a claimed one. |
| 2026-09-09 | A production deploy refuses a commit whose `ci.yml` run is not green. Which run, now that the trunk tier is path-scoped? | The run of the ref being deployed. `ci.yml` runs on every `<project>-v*` tag with every job (`all=true`), and `_deploy-compose.yml` selects the run whose head branch is the ref it deploys: the tag for production, `main` for a preview, which is the run that triggered it. | A docs-only commit after a red change to a project gets a trunk run where every job of that project is skipped and `ci` concludes success; a tag on that commit shipped the red code (ORB-28). A release now costs one full CI run, all projects, and the deploy runner waits for it; releases are rare, and the alternative, asking the API which jobs ran, puts a per-project job list into the shared mechanism. |
| 2026-09-09 | Invoicing runs late: August's work is issued in September, and the period P&L attributes revenue by `data_emissione` (slice 4 §7.1), so a month-by-month view is skewed every time. Does the report switch to the accrual period? | No. Revenue by emission date stays the default reading, and the fiscal reports (`economic_overview`, `fiscal_estimate`) never take another. A second reading exists beside it: `GET /api/analytics/pnl?base=competenza` and `get_period_pnl(base="competenza")` attribute each invoice to `coalesce(competenza_da, data_emissione)`, where `competenza_da`/`competenza_a` is the accrual period the document declares at header level, frozen at issue and written on every `DettaglioLinee` of the XML (ORB-61). | Two readings of one figure, named, rather than one figure whose meaning changed under everyone: §7.1 chose emission on purpose and the fiscal reality is by emission or by cash. Costs and hours are attributed by their own date under both readings; only the invoice moves, and only when it declared a period. A proforma is not revenue under either. |
| 2026-09-09 | The pre-check accepts what the writer serialises: which checks were still missing from it, and where does a foreign customer's fiscal identity go? | Two. The character set, `_LATIN_RE`, now runs in `check_party_exportable` with the writer's own message and tag, through one `_latin_message` both call. And a recipient needs an `IdFiscaleIVA` or a `CodiceFiscale`: `check_recipient_identity` refuses one with neither, naming `partita_iva`, because that is where a foreign register's number belongs. `CodiceFiscale` stays the Italian register's code and a foreign identifier is never written into it. | The rule from ORB-38 holds for every constraint the writer applies, not only for the address, and `issue` calls each check before it touches the counter. The identity rule is not in the schema: `IdFiscaleIVA` and `CodiceFiscale` are both `minOccurs="0"` in `DatiAnagraficiCessionarioType`, so the document validates and the SdI rejects it with control 00417 of the Elenco dei controlli, which is why the exporter has to know it. A refusal before the number is spent costs one correction; after, it costs a hole in the register (ORB-56). |
| 2026-09-09 | A document's address line: assembled in the template, or computed in the code? | Computed. `invoices/pdf.py::indirizzo_display` builds it and both invoice templates print `{{cliente.indirizzo_display}}`. Italy keeps `CAP Comune (PR)`; outside it the postcode is the one the record holds and the province is not printed. A record with no province loses the parentheses instead of printing them empty. | The template has no punctuation that depends on a value being present. `({{cliente.provincia}})` was hard-coded, so a London customer read `EC1V 9HL London () GB` on the PDF (ORB-55), and the same hole was open on an Italian record with no province yet. Every other value these templates read is already a string `build_scope` formatted, and the PDF prints the stored postcode while the XML carries the SdI's `00000`: two audiences, one record, and the difference belongs in code that can explain itself. |
| 2026-09-10 | The history carried real clients, a real fiscal identity, a signature and two third parties' contact details (ORB-46..52). It is rewritten with `git filter-repo`, but 33 `refs/pull/N/head` on the origin still pin every pre-rewrite commit, and neither a force-push nor any API call can remove them. Publish anyway? | No. The purged history is pushed to a **new** repository of the same name and that one is made public; the old repository is renamed `orbiters-archive` and stays private, with its pull requests and its pre-rewrite objects inside it. Both histories are kept as bundles outside any repository (`~/backups`, 0600). | A repository that has ever carried unpurged history is never the one that gets published: a rewrite plus a force-push leaves the old objects reachable through refs nobody can delete, and asking GitHub Support to purge them is a request, not a guarantee. Going public is therefore a fresh remote, not a visibility flip, and the archive is deleted only when somebody decides the pull request threads are no longer worth keeping. |
| 2026-09-10 | Under which licence does the repository go public? | GNU AGPL v3 (`LICENSE`), Lorenzo's call on 2026-09-10. | Self-hosting is free and a modified version offered as a network service owes its source to its users, which is the shape of a self-hostable product that is also sold as a service. `CONTRIBUTING.md` keeps the licence among the decisions that are not an agent's to take. |
| 2026-09-10 | The repository went public on 2026-09-10 and hosted Actions minutes are free now, so the reason the trunk tier gave up "the trunk proves the whole tree on every commit" (2026-09-09 row) no longer holds. Go back to running every project on every push? | No: the scoping on `push` stays, because a fifteen-minute trunk run on a docs-only commit is still a cost, just in waiting rather than in money. `ci.yml` instead gains a nightly `schedule` run on `main` (`17 3 * * *`, UTC; first fires 2026-09-11 03:17 UTC) that proves the whole tree without putting it on the critical path of a merge (ORB-85). | The nightly run costs no new mechanism: a `schedule` event carries no `before` at all, so it earns `all=true` through the same "no usable base commit" branch a force push or a release tag already take, rather than a fourth branch written for it. It also cannot start a deploy: `deploy-*.yml`'s `workflow_run` guard already requires `github.event.workflow_run.event == 'push'`, and a scheduled run's own event is `schedule`, so the guard excludes it with no change to the deploy files. `ci` stays the one aggregate status check either way, since the schedule adds no job and touches neither its `needs` list nor its name. |
| 2026-09-10 | Same day, hours later: `orbiters-archive` still held every pre-rewrite object and the 33 pull request threads, privately and with no end date (ORB-83). Keep it as the readable record of the first month? | No, deleted (`DELETE /repos/joinorbiters/orbiters-archive`, 204, the URL answers 404). The pre-rewrite history and the pull request threads survive only as `~/backups/orbiters-pre-rewrite-*.bundle` (1,242 commits, `git bundle verify` complete) and `~/backups/orbiters-github-*.json`, both 0600 on the devbox. | 2026-09-10 | The repository is public and `main` had no protection of any kind (ORB-44). What is enforced, and who may bypass it? | Two rulesets, both `active`, no bypass actors. "main: pull request and green ci" refuses a direct push, a force-push and a deletion of `main`, and requires a pull request whose `ci` context is green, with **zero** required approvals. "release tags are immutable" refuses a deletion or a non-fast-forward on any tag. | The approval count is zero on purpose: two people merge their own work here with agents, and a review requirement neither of us can satisfy alone would be bypassed within a day. What is worth enforcing is the two things a hurry actually breaks, a merge with red CI and a rewritten tag. An emergency edits the ruleset, in public, instead of using a private bypass nobody sees. |
| 2026-09-10 | The hub's admin area and its two public wizards share one `tokens.css`, copied from the CRM's application shapes (`--radius: 10px`, a blurred `--shadow-lg`), while `joinorbiters.com`'s own pages draw no radius, a solid 2px ink border and a stepped offset shadow instead (`landing.css:9`, `landing.css:31`). The chooser, the two wizards and the thanks page are reached mid-sentence from the landing's own call to action (ORB-73): which system do they follow? | The site's. `projects/hub/apps/web/src/styles/tokens.css` gains a `.site` scope restating the landing's own values -- `--radius: 0`, a solid ink `--border`/`--input`, an 8px/6px offset `--shadow-xs`..`--shadow-lg`, and the `--landing-*` colours, which already equal the application's own `--primary`/`--ring` -- for whichever element carries that class. ORB-74 (page chrome) and ORB-75 (fields and buttons) apply the class and the component shapes; this decision changes no markup. |
| 2026-09-10 | Ivan's issued invoices are the previous system's PDFs, kept at import; a proforma rendered by PigroCRM sat beside them looking like another product («la proforma non ha il template uguale a quella delle fatture», ORB-102).
